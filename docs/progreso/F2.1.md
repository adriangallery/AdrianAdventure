# F2.1 — Relay `/funtico` en el save-server, apagado por defecto (21-nov-2026)

Plan: FUNTICO_ADVENTURE. Solo servidor y tests: nada en `src/` (el puente sigue igual; usarlo es F2.3).

## Qué hay
- `save-server/funtico.js`: el relay, sin framework (como `stats-routes.js`). `index.js` lo monta en `/funtico` y
  `/funtico/*` (GET y POST). Desde fuera: `https://funtico.adventure.adrianzero.com/save-api/funtico/...` → nginx →
  `/funtico/...`. Mismo origen que el juego: **no se abre CORS nuevo** (la lista de orígenes no cambia).
- `save-server/funtico-crypto.js`: `CryptoHelper` del SDK reimplementado con `node:crypto`, funciones puras sin
  singleton, más la derivación de claves de cada método del SDK.
- Tests: `npm run test:funtico-server` (`tests/funtico-crypto.test.mjs`, `tests/funtico-relay.test.mjs`), en `lint.yml`
  justo después de `test:server`. Los de `test:server` no se tocan.

## Variables (config de Dokku del save-server)
| Variable | Qué | Por defecto |
|---|---|---|
| `FUNTICO_ENABLED` | `1`/`true`/`yes`/`on` enciende. Apagado: **todo** `/funtico/*` es 404, no se lee ninguna otra variable y no se crea nada en el volumen | apagado |
| `FUNTICO_ENV` | `staging` → `https://funtico-sdk-staging.azurewebsites.net`; `production` (o `prod`) → `https://funtico-sdk.azurewebsites.net` (las del SDK) | `staging` |
| `FUNTICO_PUBLIC_KEY` | clave pública del juego; el relay la pone como `X-User-Key` en todo lo que sale (la del cliente se ignora) | — |
| `FUNTICO_PRIVATE_KEY` | clave privada REAL. Solo aquí; nunca en repo, build ni logs | — |
| `FUNTICO_CLIENT_PAD_KEY` | relleno PÚBLICO que el cliente pasa al SDK como `privateGameKey` | `public-placeholder-not-a-secret-zeroadventure` (= `FUNTICO_PLACEHOLDER` del puente; un test lo comprueba) |

Encendido con claves ausentes o inválidas → todas las rutas 503 y **un** aviso en el log con el motivo, sin el valor.
Reglas = las de `validateConfig` del SDK (no vacía, sin espacios alrededor, privada ≥ 8 —aquí ≥ 9, porque la firma usa lo
que va desde el carácter 8—, distinta de la pública y sin solaparse) y además el relleno ≠ la privada. **No** se exige
longitud exacta: el SDK lo prohíbe expresamente («keys are issued in more than one format»).

## Lista blanca (método + ruta exactos; lo demás → 404 sin salir a la red)
| Ruta | Método del SDK | Tipo |
|---|---|---|
| `POST /Auth/funtico-auth` | `Initialize`/`Authentication` | reenvío (cuerpo `{Token}` solo) |
| `GET /User/get-full-data`, `/User/get-balance`, `/User/vouchers` | `GetUserData`, `GetBalance`, `GetVouchers` | reenvío |
| `GET /HallOfFame/global`, `/HallOfFame/monthly` (`page`, `limit`, `gameMode`) | `GetHallOfFame` | reenvío |
| `GET /Campaign/availability` (sin login), `GET /Campaign/levels` | `GetCampaignAvailability`, `GetCampaignLevels` | reenvío |
| `POST /Campaign/start-level` (`levelId`) | `StartCampaignLevel` | reenvío |
| `GET /Session/any-unfinished-sessions`, `GET /Session/reconnect-to-session` (`id`) | `UserHasUnfinishedSession_Client`, `ReconnectToUnfinishedSession_Client` | reenvío + `Data` re-cifrado de la real al relleno |
| `POST /User/complete-practice` | `CompletePractice` | **firmado** |
| `POST /Campaign/complete-level` | `CompleteCampaignLevel` | **firmado** |
| `POST /Session/create-session`, `POST /Session/update-session` | `CreateSession_Client`, `UpdateSession_Client` | **firmado** (re-cifrado) |

Solo se aceptan los parámetros de query de la tabla (valores `[A-Za-z0-9_.:-]`, sin repetir); el host sale de
`FUNTICO_ENV` y nunca del cliente; `redirect: 'error'`. Lo que sale lleva solo `X-User-Key` (config), el
`Authorization: Bearer` del jugador y `Content-Type`. **Nunca** `X-Server-Key`. Al cliente vuelve solo estado y cuerpo
(ninguna cabecera de Funtico). Timeout (10 s) o red caída → 502 `{"error":"Upstream unavailable"}`. Cuerpo > 64 KB → 413.

## Esquema de cifrado (el del SDK, público en su repo)
AES-128-CBC/PKCS7 con IV fijo y clave de texto ajustada a 16 caracteres; firma HMAC-SHA256 en hex. Por ruta:
- Practice: clave = 8 dígitos del `UserId` + 8 primeros de la privada; firma con la privada desde el carácter 8.
- Campaña: clave = 8 primeros del `AttemptId` + 8 primeros de la privada; misma firma.
- Sesiones: clave = `UserId` en hex + 8 últimos de la privada; firma con el `SessionId` (no secreto).

Flujo de un envío firmado: (1) forma del cuerpo exterior; (2) para Practice/campaña, la firma con el **relleno** se
comprueba ANTES de nada (manipulado → 400 sin red); (3) `UserId` preguntado a Funtico con el token del propio jugador
(`/User/get-full-data`, caché 5 min por hash del token: no se fía del cliente); (4) descifra con el relleno y valida la
forma del texto (Practice: `Score` int32, `RunId`, `Collected`, `GameEvents`; campaña: `AttemptId` = el exterior,
`LevelId`, `Metrics` 1–32 números; sesión: JSON); (5) validador enganchado; (6) re-cifra y firma con la **real**.

`update-session` no lleva el `SessionId` que hace falta para la firma: el relay lo aprende de las respuestas de
`create-session`/`reconnect-to-session`/`any-unfinished-sessions` (en memoria, ligado al `UserId`). Si no lo conoce
(p. ej. tras reiniciar el save-server) → 409 «reconnect first». Ver dudas.

## Datos
`<SAVE_DIR>/funtico/` (solo con el interruptor encendido). `signed.jsonl`: una línea por envío firmado reenviado,
`{t, route, status}` (hora, ruta y estado HTTP de Funtico); sin tokens, ids ni cuerpos. `/leaderboard` no lo lee
(no es un `.json` de la raíz).

## Enganche para F2.2
```js
createFunticoRelay({ env, dataDir, validators: {
  'POST /User/complete-practice': async (payload, ctx) => …,   // ctx = { route, userId, now }
  'POST /Campaign/complete-level': async (payload, ctx) => …,
  'POST /Session/create-session' | 'POST /Session/update-session': (stateJsonString, ctx) => …, // ctx.sessionId
}})
```
Devuelve `undefined`/`true` (sigue igual), `{ ok: false, status?, error }` (rechaza; 4xx, 400 por defecto, el `error` va
al cliente) o `{ ok: true, payload }` (sustituye: p. ej. la puntuación recalculada de Triage). Lo sustituido se vuelve a
validar en forma antes de firmar. Si lanza → 500 genérico. F2.2 añadirá `POST /funtico/run/start` como ruta propia
(hoy no existe: sería 404) e inyectará los validadores desde `index.js`.

## Cómo se activa (F2.3)
1. `dokku config:set` del save-server: `FUNTICO_ENABLED=1 FUNTICO_ENV=staging FUNTICO_PUBLIC_KEY=… FUNTICO_PRIVATE_KEY=…`
   (de `macmini:~/.secrets/funtico-staging.env`; nunca en el repo).
2. Cliente: `publicGameKey` real de staging en el puente; `apiBaseUrl` ya es `<origen>/save-api/funtico` y el relleno ya
   es `FUNTICO_PLACEHOLDER`.
3. Comprobar: `curl …/save-api/funtico/Campaign/availability` responde lo de Funtico; con el interruptor apagado, 404.
Vuelta atrás: `FUNTICO_ENABLED` fuera (o `0`) y reinicio; o revert del merge.

## Dudas / límites
- El mapa `Id → SessionId` de `update-session` vive en memoria: tras un reinicio, la primera actualización da 409 hasta
  que el cliente reconecta. Si molesta en F2.3, persistirlo en `<SAVE_DIR>/funtico/`.
- `any-unfinished-sessions` y `reconnect-to-session` se re-cifran al relleno para que el SDK del cliente las pueda abrir.
- Sin límite de ritmo propio todavía (lo pone Funtico y la validación de F2.2).
- El montaje en Hono (`index.js`) no tiene test propio (como `/stats`, se prueba el manejador puro); `node --check` OK.
